# 视频审阅与协同进化执行协议

## 1. 输入

优先接收生成 Skill 提供的 `qa/review-handoff.json`。没有 handoff 时，仍可
审阅，但必须把合同覆盖、稳定锚点和有意选择标记为信息不足。

必需输入：

- 最终视频文件；
- 生成 Skill 和审阅 Skill 的版本；
- brief、内容合同或明确的用户目标；
- 已知的有意选择：允许的重叠、黑场、静音、透明、非写实物理等；
- 审阅范围和不检查项。

可选高价值输入：

- 分镜、timeline、镜头 ID、提示词、参考、模型和参数；
- 关键帧、技术报告、已有缺陷记录；
- 已知干净样片与已知问题样片；
- 用户可供确认的审美或业务偏好。

媒体可访问时，不先询问用户发现了什么问题。先独立审片并给出首轮问题。

## 2. 锁定与校验

1. 计算最终媒体的 SHA-256 和大小。
2. 读取容器、codec、分辨率、帧率、时长、音频和字幕状态。
3. 校验 handoff 中的媒体哈希、Skill 版本、镜头锚点和有意选择是否与当前
   文件一致。
4. 文件改变时，旧 review receipt、规则验证和交付状态全部失效。
5. 检查审查材料是否来自当前最终文件，而不是 animatic、源码断言、历史
   报告或模型成功响应。

## 3. 分层检查

按“低成本、高确定性 -> 高成本、需语义判断”执行。

### L0 · 意图与合同

- 目标观众、用途、平台和交付承诺；
- 必需项、禁止项和签名事件；
- 有意风格、允许重叠、允许黑场、允许静默和其他豁免；
- 稳定镜头/事件锚点和可剪辑关系。

合同缺失时，只降低依赖合同的结论置信度；不要停止可以独立证明的技术检查。

### L1 · 技术

- 完整解码；
- 容器、codec、raster、fps、时长、颜色和音频规格；
- 黑帧、冻结、闪帧、静音、削波和明显异常；
- 最终文件哈希。

自动检测结果是候选事件，不是审美结论。黑场、静默或冻结可能与意图一致。

### L2 · 静态内容、文字与版式

- 必需主体、产品、身份、场景和内容真实性；
- 文字逐字内容、字形、断行、裁切和安全区；
- 文字与装饰线、图形、边框、其他文字、人物或产品的重叠；
- 前景/背景、支撑、接触、水线、透明、阴影、反射和合成边缘；
- 目标观看尺寸与原生分辨率下的对比和细节。

文字检查必须同时完成：

1. 内容与字形；
2. 版式与图文关系。

只完成第一项不能判定“文字没有问题”。

任何重叠都按 `quality-standard.md` 判断是
`intentional-supported`、`intentional-ambiguous`、
`accidental-harmful` 或 `insufficient-evidence`。

### L3 · 运动与时序

- 起始状态、主动作和结束状态；
- 方向、速度、节拍、加速度和连续性；
- 接触、支撑、滚动、变形、穿透、融合和分离；
- 相机路径、主轴、视差、屏幕方向和转场；
- 周期图案在交付帧率下的混叠、停走或反向；
- 细线、高光、透明物和遮罩的逐帧稳定性；
- 文字/图形覆盖随时间的出现、保持和消失。

单帧可证明版面问题；动作、方向和稳定性需要连续帧或实际播放。

### L4 · 语义、编辑与音频

- 观众能否理解目标信息；
- 注意力、节奏、信息顺序和可剪辑性；
- 旁白、对白、音乐、效果声的层级与可懂度；
- 声画同步、字幕与语音、声音与动作节拍；
- 是否存在“每个局部都正确，但整体不对”的问题。

无法主观听审时，只能报告技术测量和可验证的同步事实。

### L5 · 定向证据

对每个可能的 blocker 或 major：

- 用稳定锚点和时间窗建立最小检查包；
- 读取原生分辨率帧、连续帧条带、局部裁剪或短包络；
- 检查多个时刻，不只挑一个有利帧；
- 证据必须能区分真实缺陷与有意设计。

### L6 · 冷审

当独立性可用时，使用未看到生成过程和第二轮修复的新审阅者。至少提供：

- brief 和允许选择；
- 当前稳定文件；
- 已知干净对照；
- 盲于旧分数、A/B 身份和预期答案的评分条件。

没有独立审阅者时，明确说明这是 self-review。

## 4. 首轮问题报告

先报告自审结果，再邀请用户纠正。问题格式：

```text
issue_id:
anchor:
media_sha256:
timecode / frame range:
observed:
expected_source:
overlap_or_intent_judgment:
verdict:
severity:
confidence:
impact:
evidence:
```

补充要求：

- 每个结论绑定当前文件；
- 不因某帧、某个固定时间码或某个主体发明全局规则；
- 不为了填满表格制造问题；
- 只给问题时，不写根因和修复；
- 用户要求根因时，再区分直接原因、上游诱因和责任层；
- 对无法完成的项目明确写 `not_checked` 或 `insufficient_evidence`。

推荐结尾：

> 以上是首轮自审。请指出漏报、误报、表示意图或需要补充的验收条件；
> 我会逐条复核，并把项目修正与候选通用规则分开记录。

## 5. 校准

收到用户反馈后：

1. 重开同一文件和同一时间范围；
2. 区分事实纠正、审美偏好、硬性要求和生成限制；
3. 对每个相关 finding 标记维持、升级、降级、撤回或改为条件确认；
4. 如果这是漏检，记录漏检类别：
   - `fact_miss`；
   - `classification_error`；
   - `expectation_error`；
   - `evidence_gap`；
   - `toolcapability_gap`；
5. 不改写旧记录；追加新 revision 并通过 `supersedes` 指向被替代记录；
6. 若纠正改变通用规则，先降为候选并设计正反例。

## 6. 生成侧变更请求

确认问题后，判断最小修复层并生成一条
`generation_change_request`：

- 目标生成 Skill 版本和章节；
- 关系原语与触发条件；
- 当前可观察失败；
- 期望可观察结果；
- 保留项和禁止退化项；
- 正向测试、负向测试、跨路线测试；
- 成本、风险和回退条件；
- 建议作用域和规则 ID。

默认不直接修改生成 Skill。`coevolve` 模式且用户明确授权时，才可提交修改。

## 7. 回归与规则升级

每次修复后：

1. 原失败案例必须从 fail 变 pass；
2. 已知干净对照不得新增阻断；
3. 至少两个不同内容案例共享同一关系原语；
4. 至少一个不同生产路线或更高复杂度案例；
5. 加入合理反例；
6. 比较缺陷率、严重度、误报率、身份/动作/镜头/文字、时序、可剪辑性、
   创意多样性和成本；
7. 随机生成路线比较整体通过率和最差输出，不只挑最好输出；
8. 同类原因连续三次未修复即停止并升级给用户。

只有回归通过后才能把规则从 `candidate` 改为 `validated`。

## 8. 记忆写入

1. 追加 issue revision；
2. 追加或修订 rule record；
3. 如有作用域或触发条件变化，更新 `quality-standard.md`；
4. 运行：

```bash
python scripts/validate_memory.py
```

5. 报告新增、修订、拒绝或合并的规则，以及它们对下一次审阅的影响。

## 9. 提交前自查

- 文件哈希和版本是否锁定？
- 是否真的看过最终输出？
- 是否检查了文字内容与图文关系两件事？
- 是否把设计性重叠误判为错误？
- 是否用单帧判断运动？
- 是否用了稳定锚点而非只有时间码？
- 是否把低分辨率总览当成原生证据？
- 是否被旧 QA 的 pass 锚定？
- 是否区分事实、推断、偏好和硬要求？
- 是否制造了不存在的问题？
- 是否把项目规则写成全局规范？
- 是否记录了未检查项和反例？
